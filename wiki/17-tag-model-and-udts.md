## 1. Purpose

This page states the tag model that the Cadre HMI Components library reads, as one Ignition UDT (user defined type) per device kind, plus the
interlock condition and summary structures. For each member it gives the data type, the access, the write path and role that writes it, the
faceplate tab that shows it, whether the generated test model creates it, its alarm and history configuration, and the entry of the device
model (`cadre-hmi-devices/1`) that a builder writes for an instance.

Two readers use it. An automatic view builder (a tool that writes the screen descriptors and the device model, for example ctig from the
devices of a Citect project) needs to know which members a device kind may carry, in what types and with what access, so that the device model it
writes passes gate G7 devices. A tag engineer needs to know which tag structure each kind needs, so that the UDT definitions and the source
tags exist before the builder runs.

Every fact on this page traces to `library/profile.json`, to the code named in the header table, to a page of this wiki or to a measured gateway
fact of page 07. Where this page and the code differ, the code and the profile govern, and the difference is reported in section 11. The UDT
definitions are not shipped as an importable file; the JSON of section 9 is the shape to import, built on the keys that experiment E6 measured
(GF-54).

## 2. The Principle

### 2.1 A Device Is a Tag Folder

A device is a tag folder. The device model names it by `id` under `tagRoot`, so that its path is `<tagRoot>/<id>`, and every member is addressed by
its name relative to that folder: `state`, `speedSp`, `mnt/forceOn`, `cfg/startDelay`, `ilk/permitted`, `ilk/C01/ok`. A tag name never contains a
slash (GF-11: the import rejects it), so each segment of a member path is a folder: the subfolders are `mnt/` (maintenance), `cfg/`
(configuration), `ilk/` (the interlock summary) and `ilk/Cnn/` (one condition, nn from 01).

A UDT instance is such a folder. Its members are those of the definition, and `system.tag.exists` answers True for the instance and for each of its
members and False for a member the type lacks (GF-54). That is the test the faceplates use: each polls `cadre.hmi.device_read`, which looks for every
member with `system.tag.exists` and reads the members present in one call (page 13 section 9.1). A UDT therefore needs no special support in the
library; the library reads the folder.

### 2.2 Every Member Is Optional

No member is required (the `required` flag of every member of every kind in the profile is false). A faceplate lists the members its device carries
and hides the rest, a row, a section title or a command group at a time (page 13 section 9.1 rule 1). Two consequences bind the tag engineer.

1. **The device model lists exactly the members the folder carries.** Gate G7 devices fails a device model that lists a member the tag model lacks,
   and fails a tag folder that carries a member of the library's profile for the kind which the model leaves out, since the faceplate would show it
   (section 10).
2. **A member must have a source.** A reference tag whose source does not exist still exists, reads null with a bad quality, and the faceplate
   states it on a line beneath the tab row, which gate G11 fails on (GF-50, page 13 section 9.1 rule 3). A member with no source must therefore not
   be created at all. A UDT instance carries every member of its definition, so a definition holds only the members that all its instances have, and
   kinds of device that differ in their members take one definition for each variant (section 3.2).

### 2.3 Data Types

The device model names a member's type from the set Boolean, Int1, Int2, Int4, Int8, Float4, Float8 and String (`schemas/devices.schema.json`).
The column Type of the tables below is the type the library reads. Gate G7 devices accepts a declared type that suits it (`_suits`): a Boolean and a
String exactly; for a member the library reads as an integer (Int4, Int8), any integer type; for Float8, any number, since a source may hold a value in
a narrower type. A UDT member takes the same `dataType` as the device model entry for it (the gate compares the two, section 10).

### 2.4 The Device Model Entry

The device model entry of an instance is derived from its UDT and its source. Table 1 gives each key and the rule a builder follows.

Table 1. The keys of a device model entry and where each comes from.

| Key | Rule |
|---|---|
| `id` | The instance's folder name under `tagRoot`: letters, digits, underscore and hyphen, with `/` only between folders (schema pattern) |
| `kind` | A kind of Table 2; it selects the faceplate and the members the device may list |
| `title`, `label`, `unit` | The identifier shown in the faceplate header, the description beneath it and the unit of the value; else those of the descriptor's symbol |
| `members` | One key for each member the instance carries, by relative name, with `type` (the UDT member's `dataType`) and `access` |
| `members[].access` | `write` for a member on a write path (Table 16) whose tag accepts a write: a memory tag, or a reference whose source accepts one; `read` for every other member, and for every expression tag (GF-49) |
| `members[].pulse`, `caption` | `pulse` true on every member of the kind's `pulses` that is marked `write`; `caption` only on such a member (section 5.7) |
| `members[].config` | The Config row of a member under `cfg/` (section 5.4) |
| `alarmSources` | The source patterns of the device's alarms where they stay on source tags (section 7.4) |
| `trend` | The members the tag model historises, each one the device lists (gate G7 devices); each gets a card on the trend page, and the faceplate's trend draws those among the kind's trend members (section 8) |
| `faceplate` | `openbridge` or `asm`; left out, the project's default (`screen.py --faceplate`) |
| `modes` | The values of the member `mode`, each with a name and an owner (section 5.5) |
| `node` | The device's node of the plant hierarchy, for a device no page draws |

## 3. Definitions and Instances

### 3.1 Where the Definitions Sit

A UDT definition is found only under the provider's own `_types_` folder. A `UdtType` imported inside a `_types_` folder nested in another folder is
dropped without an error (GF-51). The definition `Cadre/Pump` therefore sits at `[default]_types_/Cadre/Pump`, and an instance names it by
`typeId` `Cadre/Pump`, the path below `_types_` (GF-54). The document that carries it is a folder named `_types_`, imported at the provider root, as
experiment E6 imported it (`tools/experiments/e6_adapter_probe.py`, `types_document` and `deploy.import_tags("default", "", document)`): the types first,
then the instances. Writing under `_types_` is outside the tag folders the library's own sessions write, and on the owner's local gateway it needs the
owner's authorisation (COBD-035); the cloud gateway is throwaway and needs none.

### 3.2 Recommended Names

The names of Table 2 are this page's recommendation. The library reads only member names, relative to the device folder; it never reads a UDT name
or a `typeId`. A site may name its types otherwise without any change to the library, the device model or the descriptors.

Table 2. The recommended UDT for each device kind, with the faceplate each kind opens.

| UDT (`typeId`) | Device kinds | Stock faceplate | ASM faceplate |
|---|---|---|---|
| `Cadre/Pump` | pump, motor, fan | `Faceplate/Pump` | `Faceplate/ASM/Pump` |
| `Cadre/Valve` | valve, analogvalve, damper | `Faceplate/Valve` | `Faceplate/ASM/Valve` |
| `Cadre/Tank` | tank | `Faceplate/Tank` | `Faceplate/Tank` |
| `Cadre/Instrument` | instrument, readout, instrument-field | `Faceplate/Instrument` | `Faceplate/ASM/Instrument` |
| `Cadre/Controller` | controller | `Faceplate/Controller` | `Faceplate/Controller` |
| `Cadre/Indicator` | indicator | `Faceplate/Input` | `Faceplate/Input` |
| `Cadre/Sequence` | sequence | `Faceplate/Sequence` | `Faceplate/ASM/Sequence` |
| `Cadre/Generator` | generator | `Faceplate/ASM/Generator` | `Faceplate/ASM/Generator` |
| None: a local device has no UDT of its own (section 4.9) | local | `Faceplate/ASM/Local` | `Faceplate/ASM/Local` |
| `Cadre/InterlockCondition` | one condition `ilk/Cnn/` | the Interlocks tab | the Interlock tab |
| `Cadre/InterlockSummary` | the summary `ilk/` | the Interlocks tab | the Interlock tab |

Rules for the choice of definitions:

1. Kinds that share members may share a definition, but the device model's `kind` still decides the faceplate. A fan and a pump with the same
   members may be instances of `Cadre/Pump` with `kind` `fan` and `pump`.
2. A kind that some devices carry with maintenance members and others without takes two definitions (for example `Cadre/Pump` and
   `Cadre/PumpBasic`), by section 2.2 rule 2. The same holds for any optional group: limits, delays, range flags, `cfg/` rows, `ilk/`.
3. The members `cfg/<name>` differ from site to site (their names are free, section 5.4), so a definition holds the `cfg/` members of the
   devices it serves.

### 3.3 Parameters

A definition takes one `String` parameter, `Stem` in the probe, with which a member forms its source path. The measured forms (GF-54) are a
`sourceTagPath` and an `expression`, each written as `{"bindType": "parameter", "binding": "...{Stem}..."}`:

```json
"parameters": {"Stem": {"dataType": "String", "value": ""}},
"sourceTagPath": {"bindType": "parameter", "binding": "[default]plant/src/{Stem}_Run"}
```

An expression written as a plain string that contains `{Stem}` reads null with the quality `Error_Configuration`: the parameter form is
needed (GF-54). The instance sets the parameter, `"parameters": {"Stem": {"dataType": "String", "value": "P101"}}`, and lists a stub for each member
(`{"name": "state", "tagType": "AtomicTag"}`), as the export of the probe returned it.

A site whose members read an OPC item would bind `valueSource` `opc` and `opcItemPath`. GF-51 records that the Ignition-Wiki (IGW:26) documents the
parameter form for `opcItemPath` and for `value`; experiment E6 measured the form on `sourceTagPath` and `expression` only (GF-54), so the OPC form
has not been measured here. This page therefore gives no other OPC key; they are taken from
the schemas vendored in `cloud/vendor/ignition-wiki/` and measured before use (section 11).

### 3.4 Value Source by Access

Table 3. What a member's `valueSource` may be, by its access.

| Access | `valueSource` | Notes |
|---|---|---|
| read | `reference`, `expr` or `memory` | A reference passes a source value through (GF-54); an expression computes (the sample's `state`, `level`, `ok`); a memory tag holds a simulated value |
| write | `memory`, or `reference` to a source that accepts a write | A write to a reference tag reaches the source (GF-54). An expression tag refuses a write with `Bad_ReadOnly` (GF-49), and gate G7 devices fails a member marked `write` that is an expression tag |
| pulse | `memory` or `reference` | The library writes true (W18) and the plant returns false. A memory pulse needs a value-changed script (`eventScripts`, GF-57) in a simulation; the plant's controller does it otherwise |
| configuration | `memory` or `reference` | Written by W19 within the bounds of the model (section 5.4) |

## 4. The Members of Each Device Kind

Every table of this section lists the members of the kind in the library profile (`deviceKinds`), in alphabetical order, except those under `mnt/`
(Table 12), `cfg/` (section 5.4) and `ilk/` (section 6), which apply to a kind as its facts state. The columns are:

* **Type**: the type the library reads (section 2.3).
* **Access**: `read`, or `write` with the write path of Table 16; every path needs the role `Administrator` (COBD-024), so the role is not repeated.
* **Test model**: whether the generated test model creates the member for a device of a build without a device model, with its default
  (`FACEPLATE_MEMBERS` of `tools/hmi/screen.py`). It writes a memory tag of the library's type for each, in folders by path segment, and beyond them
  only the members the descriptor's symbols bind and the tags the page parts read (`tags_document`, page 06 section 5 rule 3). For a device that a
  device model names it creates the members the model lists, in the model's types, with the value false, 0 or empty text unless the descriptor's
  `tagValues` or a bound value gives another, beside the members the symbols bind.
* **Tab**: the tab that shows the member, in the stock faceplate and then in the `asm` one, separated by a slash; one word where the two agree and
  `None` where a style shows nothing. The `asm` Diagnostics tab also shows the raw value of a fixed set of members (page 13 section 10.2 Table 1):
  for the pump and the valve every member the faceplate reads (`framework.DIAGNOSTIC_GROUPS`), and for the generator, the sequence and the
  instrument the groups of `tools/hmi/devices_asm.py`, which leave out the `mnt/` members and the instrument's limits; `None (relay)` marks a member that no tab shows.

Pump, motor and fan carry the same members and open `Faceplate/Pump` (stock) or `Faceplate/ASM/Pump` (`asm`).

| `fault` | Boolean | write (W5) | Yes, False | Control / Home | Fault; Reset fault writes false where the member is writable |
| `mode` | Int4 | write (W2) | Yes, 0 | Control / Home | Control mode number; reading by the `modes` list, else 0 Auto, 1 Manual, 2 Local; written by the mode buttons |
| `speed` | Float8 | read | Yes, 0.0 | Control / Home | Speed in per cent |
| `speedSp` | Float8 | write (W3) | Yes, 80.0 | Control / Home | Speed setpoint in per cent, 0 to 100; written by the setpoint field |

* **Symbol parameters.** The symbol's `on` and `open` bind `state` and its `speed` binds `speed`, inside the device folder (`bind_rule`, gate G7); a
  symbol bound outside the folder or to another member fails the gate (page 06 section 5 rule 2).
* **Pulses**: none. **Trend**: none.
* **Maintenance**: yes (Table 12). **Configuration**: yes (`cfg/`, section 5.4). **Interlocks**: yes (`ilk/`, section 6).

* **Note.** The profile maps `fault` to W5 for every kind, so a model may mark it `write`. A pump whose fault is a status of the source is marked `read`
  and offers no Reset fault (page 13 section 9.1 rule 2).

## 5. The Common Member Groups

### 5.1 Maintenance Members

A kind with maintenance true (pump, motor, fan, valve, analogvalve, damper, indicator, generator) may carry the members of `mnt/`. The Maintenance
tab (stock) or Config tab (`asm`) shows only for a device with a row to show: a whole force, the error mask, a flag or a configuration row
(section 5.4), and on the generator its service data (section 4.8).

Table 12. The maintenance members.

| Member | Type | Access | Meaning |
|---|---|---|---|
| `mnt/alarmSuppress` | Boolean | read | Flag: alarms suppressed |
| `mnt/errorMask` | Boolean | write (W17) | Object error mask: masked while true |
| `mnt/forceMode` | Boolean | write (W16) | Force as a mode and a value: forced while true |
| `mnt/forceOff` | Boolean | write (W16) | Force as a pair of flags: forced off; both false is automatic |
| `mnt/forceOn` | Boolean | write (W16) | Force as a pair of flags: forced on |
| `mnt/forceValue` | Boolean | write (W16) | Force as a mode and a value: the value forced to |
| `mnt/manualMode` | Boolean | read | Flag: manual mode |
| `mnt/simulated` | Boolean | read | Flag: simulated |

Rules (page 13 section 9.6, gate G7 devices):

1. **The force has two encodings** (`forceEncodings`): the pair `mnt/forceOn` and `mnt/forceOff`, or the mode and the value `mnt/forceMode` and
   `mnt/forceValue`. A device lists one whole encoding: both members of one pair, in the same access, and not both encodings. A model that lists
   one member of a pair fails. A force through the mode and the value writes the value, then the mode; a force through the pair writes the
   flag that clears, then the flag that sets.
2. **The error mask** `mnt/errorMask` is masked while true.
3. **The flags** `mnt/simulated`, `mnt/alarmSuppress` and `mnt/manualMode` are read only: no write path writes them.
4. **Writers.** The force members are W16 and the mask W17, both gated by the owner (section 5.5); a forced device shows on its symbol where the
   descriptor binds `badgeControl`.
5. **Members written must be writable** (Table 3): a memory tag, or a reference to a source that accepts a write.

### 5.2 Alarm Limits and Delays

### 5.3 The Acknowledgement Relay

Every kind may carry `alarmAck` (Boolean). A device that lists it as `write` is told of an acknowledgement of one of its alarms made through
`cadre.hmi`: the top bar's ACK (W6) and the module's alarm menu (W8, W9) write true to it, and the controller returns it to false
(`ackRelay` of the profile; page 13 section 11.5). The stock alarm table acknowledges by itself (W7, GF-40), so an acknowledgement made there is not
relayed. A device without the member is told nothing. No tab shows it.

### 5.4 Configuration Members

A configuration member is a number under the device's subfolder `cfg/`, shown as a row of the Config tab of an `asm` faceplate or of the
Maintenance tab of the stock Pump, Valve and Input faceplates (the stock Instrument and Sequence faceplates have no such tab, so the rows of an
instrument, readout, instrument field or sequence show only in the `asm` style, `framework.has_config`), and written by W19 within its bounds (page 13 section 10.4). The profile's `config` gives the prefix `cfg/`, the types Int1, Int2, Int4, Int8, Float4
and Float8, the write path W19 and a caption of at most 24 characters. A Boolean or String member has no row.

The kinds that may carry `cfg/` rows are those with config true: pump, motor, fan, valve, analogvalve, damper, instrument, readout,
instrument-field, indicator, sequence and generator. Tank and controller have none. The name after `cfg/` is free (letters, digits and
underscore; the schema's pattern for a member name), for example `cfg/startDelay` or `cfg/runTimeSP`.

The device model marks the member `config`, with a `caption` (1 to 24 characters, one line, not the label of a tab), and optionally `unit` (at most 12
characters), `minimum`, `maximum` and `format` (`0`, `0.0`, `0.00`, `0.000` or `0.0000`; `0.0` when left out). The member carries no `pulse` and no
button `caption`. Gate G7 devices requires a `cfg/` member to be marked `config`, numeric, on such a kind and with its minimum not above its maximum; it
warns of a member with no bounds. The test model of a build without a device model never creates one; with a device model it creates those the
model lists, as memory tags.

### 6.3 Rules for the Tag Engineer

1. **Numbering.** Conditions are `C01`, `C02` and on, without a gap: the faceplate lists them until the first missing one, and gate G7 fails a gap or
   a folder with no condition.
2. **Kinds and the latch.** `kind` is `permissive` or `trip` and nothing else. A trip has `latched` true (COBD-023), and the gate fails a trip that
   does not.
3. **Start and trip.** A device with interlocks starts only while `permitted` and not `interlocked`; a running device stops when it becomes
   interlocked; a permissive lost while running does not stop it. The faceplate refuses Start while the device is held (page 13 section 7 rule 1).
4. **The latch and the reset.** The Reset button writes the time of the request to `ilk/resetAt` (W11). A latched condition waits for a reset while it is
   met and was last seen not met after the latest reset. The sample keeps the time last seen not met in the condition's `notMetAt` and the latest
   request in `ilk/resetSeen`, both self references (GF-16). `resetSeen` keeps the request through an import, which returns the memory member `resetAt`
   to 0 but leaves a self reference at its value (GF-42); without it a bare import latched every trip ever reset again. A Reset pressed while the
   cause persists releases nothing, except within the expression tags' evaluation period of about 1 s.
5. **Writable members.** `ilk/Cnn/bypassed` (W10, on a condition whose `bypassable` is true) and `ilk/resetAt` (W11) are written by the library, so they
   are memory tags or references to a writable source, never expressions (GF-49).
6. **The badge.** The symbol's `badgeInterlock` follows `ilk/badge` in the sample: `interlock` while the device is held, `interlock-inhibit` while a
   condition is bypassed.
7. **The device model.** A model lists `ilk/permitted` and the other members it carries as `read`, and `ilk/resetAt` and `ilk/Cnn/bypassed` as `write`
   where the Reset and Bypass are to work: a device model that leaves them out or marks them `read` leaves the controls disabled (page 13 section 9.1
   rule 2). Gate G7 devices knows the six summary members of Table 19 and the ten condition members of Table 18; a model that lists `badge`,
   `resetSeen` or `notMetAt` fails as an unknown member.

The sample builds its conditions as plain folders with expression tags that read their own value through `{[.]name}` (`ilk_condition` and `ilk_folder` of

type, which seven members of the condition are; an instance of the condition nested in the device UDT's `ilk` folder; and an override of a member's
value in an instance. Until they are, a builder follows the sample and writes each `ilk/Cnn`
as a plain folder.

### 6.5 The Gate Checks

With `--tags-file`, gate G7 interlocks (`g7_interlocks`) walks every folder named `ilk` of the tag model and checks the six summary members of Table 19
by name and type (`ILK_SUMMARY`: `permitted`, `interlocked`, `bypassed`, `unsatisfied`, `resetRequired`, `resetAt`), at least one condition, the
numbering of section 6.3 rule 1, the ten condition members of Table 18 by name and type (`ILK_CONDITION`), a `kind` of `permissive` or `trip`, and a
`latched` value of true on every trip. It reads a folder's tags of type `Folder`, so it applies to folders as the tag file carries them (section 10 item 12).

## 7. Alarm Configuration

### 7.1 The Alarms of the Sample

The alarms of the water treatment sample (`tools/plants/wtp.py`) sit on the members below, all in the library's one form (section 7.2).

* A motor's `fault` (memory, Boolean): one alarm `Fault`, priority High.
* A tank's `level` (expression, historised): `High level` (mode `AboveValue`, following `hiLimit`, priority Medium by default) and `Low level`
  (`BelowValue`, following `loLimit`, priority High by default).
* An analyser's `value`: `High turbidity` (High, `AboveValue`, `hiLimit`, its on-delay following `hiLimitDelay`), `Low chlorine` (label text
  `Low free chlorine`; High, `BelowValue`, `loLimit`) and `Low pH` (Medium, `BelowValue`, `loLimit`).

### 7.2 The One Form

`tools/hmi/alarms.py` writes an alarm of a tag in one form, which the profile states under `alarms`, for a tool that does not import the module.

Table 20. The keys of an alarm as the library writes them.

| Key | Content |
|---|---|
| `name` | The alarm's name inside the tag, for example `Fault` or `High level` |
| `label` | `{identifier} {text}`, for example `P-101 Fault` |
| `displayPath` | `{node}/{identifier}`, for example `WTP/Intake/P-101`; the identifier alone without a node. The node is the `screen.node` of the deepest page that draws the device |
| `priority` | One of the five priorities of Table 21 |
| `shelvingAllowed` | True for every priority but Critical |
| `setpointA` | A number, or for an alarm that follows a limit `{"bindType": "Expression", "value": "{[.]hiLimit}"}` (GF-39) |
| `mode` | The sample's `AboveValue` or `BelowValue` for a limit alarm; none for a state alarm |
| `timeOnDelaySeconds` | Where the device carries the limit's delay member, `{"bindType": "Expression", "value": "{[.]hiLimitDelay}"}` (F028). This binding is recorded as to be measured on the gateway (`tools/hmi/alarms.py`, COB-143) |

| Priority | Alert colour | Shelvable |
|---|---|---|
| Critical | critical | No |
| High | alarm | Yes |
| Medium | warning | Yes |
| Low | caution | Yes |
| Diagnostic | none | Yes |

The shelving times the library's alarm tables offer are 300, 900, 1,800, 3,600, 7,200, 14,400 and 28,800 seconds, so no alarm is shelved without an
end (`shelvingTimes`, F045). A report of a state takes Diagnostic (F043), which draws no alert colour. The priority-to-colour map is that of page 13 section 11.1.

### 7.3 Alarms on UDT Members

An alarm configured on a reference tag is a second alarm beside the one on its source (GF-52). For a UDT whose members are references, the alarms
therefore stay on the source tags (section 7.4). For a UDT whose member is a memory or expression tag that owns the alarm, as in the sample, the key
`alarms` sits on the member of the definition; no measurement of an `alarms` list inside a `UdtType` member exists on page 07, and the
`{[.]hiLimit}` relative form in a UDT is likewise not measured (section 11).

### 7.4 Alarm Sources Outside the Folder

A device's alarms are those whose source lies under its folder, `prov:<provider>:/tag:<folder>/*` (GF-34; page 13 section 3). A device whose alarms stay
on source tags outside the folder lists them in `alarmSources` of its model, each pattern of the form `prov:<provider>:/tag:<path>:/alm:*`. Left out, the
alarms are those under the folder; given empty, the device has no alarm. Gate G7 devices fails a pattern whose tag part is only wildcards, and warns of a
pattern that another device's pattern overlaps and of one outside the build's alarm scope.

## 8. History

A member is trended when its tag has history enabled. In the sample the two keys are written together, `historyEnabled` true and `historyProvider`
`Sample_SQLite_Database`, the provider of the gateway (`HISTORY` of `tools/plants/wtp.py`; the cloud gateway creates it in `cloud/setup.sh gateway`).
History configured on a reference tag records the values the tag takes, and the source records nothing (GF-53), so a UDT member that is a reference may
carry the history keys itself. A site names its own provider.

Table 22. The members each kind trends.

| Kind | Main member | Also | Unit of the card |
|---|---|---|---|
| instrument, readout, instrument-field | `value` | none | the device's unit |
| tank | `level` | none | % |
| controller | `value` | `sp` (setpoint), `out` (output) | the device's unit; % for `out` |
| sequence | `step` | none | the device's unit; drawn as steps |
| generator | `engineSpeed` | `fuelLevel` (fuel level) | the device's unit; % for `fuelLevel` |

(`TREND_KINDS` and `TREND_ALSO` of `tools/hmi/screen.py`; the profile's `trend` list for each kind is the main member followed by the others.) Without `trend` in the
device model the other kinds trend nothing; with it, a device of any kind gets the cards its list names (rule 2).

1. **Without `trend` in the device model**, the trend index keeps the kind's members whose tag the tag model historises (`historised`).
2. **With `trend`**, the device's cards are exactly those members. The schema describes them as the members the tag model historises. Gate G7 devices
   checks only that each member is one the device lists; it does not read the history keys, so a `trend` member whose tag is not historised draws a card
   with no data. A builder keeps the two in step.
3. The trend page exists when at least one device has a trended member (page 13 section 8 rule 6).

## 10. Checklist for a Builder

A builder that writes tags or UDTs checks the following before it runs the generator. The items are the checks of gate G7 devices
(`g7_devices` of `tools/hmi/gates.py`; page 08 Table 4), stated in other words.

1. **Kind and identity.** Every `kind` is a kind of the profile (Table 2); no `id` appears twice; every device folder exists in the tag model.
2. **Names.** Every member is a name the profile knows for the kind (a device of the kind `local` lists any name: its names, types and write paths are not
   compared, section 4.9), or a `cfg/` member (marked `config`), or, for a kind with interlocks, one of the six summary
   members of `gates.ILK_SUMMARY` (`ilk/<member>`) or the ten condition members of `gates.ILK_CONDITION` (`ilk/Cnn/<member>`); the sample's `badge`,
   `resetSeen` and `notMetAt` of Tables 18 and 19 are unknown names to it. An unknown name is an error, never accepted in silence.
3. **Types.** Each declared type suits the type the library reads (section 2.3), and equals the `dataType` of the tag.
4. **Writes.** A member marked `write` is on a write path (Table 16), and its tag is not an expression tag. An `ilk/` member written is `ilk/resetAt` or a
   condition's `bypassed`. The gate takes the path from the member's last segment (`ILK_WRITABLE`), so without a tag file it also accepts the
   summary's `ilk/bypassed` marked `write`; a builder marks that member `read`.
5. **Pulses.** A member marked `pulse` is a pulse member of the kind, Boolean and `write`. A pulse member of the kind that is `write` is marked `pulse`. A
   caption stands only on a pulse member, is 1 to 32 characters on one line, has no space at either end, and is not the label of a faceplate tab.
6. **The force.** One whole encoding of Table 12, both members in the same access.
7. **Configuration.** A `cfg/` member is marked `config` with a caption of 1 to 24 characters, is numeric, sits on a kind with Config rows, and its minimum is
   not above its maximum. A member without bounds raises a warning.
8. **Modes.** If `modes` is given, the member `mode` is listed and whole, values and names are unique, owners are known; a device with no operator mode
   raises a warning.
9. **Trend and sources.** Each `trend` member is a member of the device. Each `alarmSources` pattern names a tag. Overlaps and patterns outside the alarm
   scope raise warnings.
10. **Descriptors.** Every symbol marked `device` names a device of the model; its kind opens the device's faceplate (otherwise `params.deviceKind`
    names it); each faceplate parameter it binds points at a member the model lists (the `bind` rule of each kind in section 4); `hasSetpoint`,
    `hasOutput` and `hasStep` belong to a device that lists `sp`, `out` or `step`.
11. **The tag model (`--tags-file`).** Each listed member exists with the declared type; no `write` member is an expression tag; the folder carries no
    member the profile knows for the kind which the model leaves out. A tag outside the profile's list (`modeBadge`, `alert`, `alertMode`, `ilk/badge`) is
    not checked, and a symbol that binds one reads it from the tag model.
12. **UDT instances in a tag file.** The gate reads the tags of the file as they stand. An instance written as the export returns it, with a stub for each
    member, has no member leaves, and the gate reports that the tag model has no folder for the device; the same device written as an expanded folder passes.
    Until a builder expands the instances (no tool of this repository does), a UDT based model is checked without `--tags-file`, and the checks
    of item 11 and of section 6.5 are done by the builder on its own tag source.
13. **Sources.** Every member has a source (section 2.2). No check of gate G7 devices reads a reference's source. A device whose members are
    references to missing sources reads null with a bad quality (GF-50), and gate G11 fails on the faceplate's quality line.

## 11. Limits and Open Items

1. **Not shipped.** The definitions are not an importable file of this repository. Section 9 is the shape to import; a builder writes the definitions
   from this page and the profile.
2. **Measured and unmeasured.** Experiment E6 (GF-54) measured a `UdtType` with a `String` parameter, reference and expression members bound by
   `sourceTagPath` and `expression` in the parameter form, an instance with `typeId` and member stubs, and the definition under `[default]_types_`.
   It did not measure: a folder (`mnt`, `cfg`, `ilk`) inside a `UdtType`; a memory member with a `value` inside a type; a `UdtInstance` nested in a
   type; the override of a member value in an instance; more than one parameter in one binding; the `alarms` list and history keys on a type member;
   `{[.]name}` relative references in a type's expression and alarm bindings; the `timeOnDelaySeconds` binding; and OPC members (`valueSource` `opc`,
   `opcItemPath`, which GF-51 records as documented by IGW:26 but not measured here). Each is to be measured on a cloud gateway before a site imports
   a definition that uses it.
3. **Provisional interlocks.** The contract stays provisional while the items of page 13 section 7.2 are open: the condition `type`, `ioFault` and
   `firstOut`, the summary's `nbOk` and `firstOut`, the core contract's request members, and the owner's review of the latch.
4. **The tag file check.** Gate G7 devices with a tag file does not read UDT instances (section 10 item 12).
5. **The trend and the history keys.** No gate reads `historyEnabled` against a `trend` list (section 8 item 2).
6. **Differences found in the sources.** (a) Page 13 Table 13 (the members of a generator) says the generator's `fault` is not written, and the profile maps
   `fault` to W5 for every kind. (b) The `asm` faceplates of the instrument and the sequence read `mnt/` members (page 13 section 12), and the profile
   gives those kinds none. (c) The gate's summary list omits `badge`, which page 13 Table 5 lists. (d) The component test page's modes (Table 15) are not the Auto, Manual and Local reading of page 06 Table 5.
7. **No position member.** The analogue valve and the damper have no position member; the library reads a state and a command only.
