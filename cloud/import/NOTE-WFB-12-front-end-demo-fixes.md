## 1. Purpose and Scope

### 1.1 The Request

The owner will record a video demonstration of a one-page migration started from the front end: stage A (the whole
project's extraction and survey, the survey card), stage B (the release, which for eng02 takes its `nothing` path),
stage C (one page picked, prepared and started), then an HTML of the new design for the owner's review before the
build, the build and import into the gateway, and the review of the side-by-side captures. No prepared page run has run
end to end. The orchestrating session found five problems that break or spoil this flow; the owner said "Yes, the five
fixes". A sixth (section 8) was found while preparing the demo's inputs: without it, step 3 refuses every stage A run.

### 1.2 Scope

In scope: the six items of sections 3 to 8; the demo's local inputs and checklist (section 11). Out of scope: any other
register item (WFB-281, WFB-286 to WFB-288, WFB-293); a module build, install or gateway restart, unless the owner
rules for it (ruling R3); a real migration run, which the owner's demo is.

### 1.3 Done Criteria

All six items are on main with their tests; `uv run wfb check` is green; the library's suite is green; the records
are updated and committed; the demo inputs are ready.

## 4. Item 2: The Release Kind's Inline Profile (WFB-290)

### 4.1 Contract

The front end shall read a start set's profile by the type its workflow declares for the run input `profile`, taken
from `manager.workflows.run_inputs(loaded.workflow)` (the spec's `type`):

1. **Type `file`** (the parent kind), or a workflow that cannot be read: the value is a path, read under the roots of
   NOTE-WFB-11 section 6.2, exactly as today (an object there is `PathRefused("not a path", outside=True)`, which the
   summary and the check show as `PROFILE_OUTSIDE`, as today).
2. **Type `json`** (the release kind): the value is the profile itself and shall be a JSON object; no path rule
   applies, and its size is bounded by the inputs file's own limit. Any other value raises
   `ValueError(INLINE_NOT_OBJECT)`, with `INLINE_NOT_OBJECT = "the profile input is a JSON object, not a path"`
   exported by `start_sets`.
3. **No `profile` input** (the assessment kind): no profile, as today.

`start_sets.profile_of(manager: Manager, workflow_id: str, inputs: Mapping[str, Any]) -> tuple[dict[str, Any], str]`
returns the profile and its source, `"inline"` or the path as `display` gives it, and raises as above.
`start_sets.summary` and `check._profile` gain the parameter `workflow_id` (after `manager`), call `profile_of`, and
their callers pass it. `profile_path` stays for `page_runs.load_base` (the parent kind only). For an inline profile
the `profile_schema` row's `observed` is "inline in the inputs file; valid against wfb.migration.profile/1" when it
validates; for `INLINE_NOT_OBJECT` the row is `fail` with `observed` exactly `INLINE_NOT_OBJECT` (no "unreadable: "
prefix) and `fix` "Give the profile as an object in the inputs file"; the summary's problem is
`f"profile: {INLINE_NOT_OBJECT}"`. Every other row is unchanged; for a release start set `page_groups` and `survey`
stay `skip` "not a page run". NOTE-WFB-11 section 6.2 is mended to this contract.

### 5.3 The Design Revised, Not Rewritten

1. **The reviewed design goes with the notes.** `wfb.migration.project_design` shall implement `prior_answer(ctx)`,
   the hook the model executor already calls (`executors/model.py` `_given_previous`, which attaches it as
   `previous_answer` only in a round that no failed round of the pass already gives one). It returns
   `(answer, framing)` when all of these hold: `ctx.pass_no > 1`; `ctx.defects_brief` starts with
   `RETURN_BRIEF_START`; and an earlier pass of the block has a passed round. The answer is that round's `answer`
   from its `outputs.json`, where "passed" means its `record.json` `status` is `"passed"` or `"reused"` (a passed round
   a rerun copied), the pass chosen is the
   highest pass number below `ctx.pass_no` that holds one (folders `ctx.round_dir.parent / "p<k>-r<m>"`; pass numbers
   may skip), and within it the highest round. The framing is: "The design you wrote before the person returned it.
   Revise it by the notes in the defects section; keep every page, mapping row, device, route and gap the notes do not
   name as it is." Otherwise it returns None, logging one line when an earlier answer exists but cannot be read, or when a round
   above the passed one has a `record.json` that cannot be read (which design the person reviewed is then unknown).
2. **The person's notes stand for the whole returned pass.** `executors/person.py` shall export
   `RETURN_BRIEF_START = "Returned from "`, and `return_brief` shall begin with it. This is an engine rule for every
   returned block in every workflow, not only the design: in `rounds.run_pass`, when the pass's first round received a
   brief that starts with `RETURN_BRIEF_START`, every later round's brief shall be that return brief as written (it ends with a blank line),
   a line break, then the round's own check brief, unchanged. `resume.prepare`, which builds a resumed round's brief itself, shall
   apply the same rule, reading the return brief from the pass's first round's `defects.md`; a round a person decided
   to repeat after an interruption is given the brief its moved folder holds. A pass without a return
   brief gives byte-identical briefs to today's. The returned blocks today: `design` (by `design_return`,
   `page_return`, `design_review`), `gap_contract` (by `contract_return`, `builder_return`), `page_loop` (by
   `review`), and those of revision 2's workflows; each now keeps the person's notes in its later rounds.

### 7.2 Contract: a Gate With No State Passes (WFB-285)

1. **The rule.** A symbol of a `diagram.GATED` kind that neither binds its state member (`bind[<state>]`) nor states
   its state parameter (`params[<state>]`) passes, as a junction does: `diagram.build_graph` gives it the passing role,
   so `compile_flow` and the reference solver `solve` agree, and no expression names it. A symbol that binds or states
   its state stays a gate, as today.
2. **The offline guard.** `screen.py`'s gate G3 (view-level keys) shall also fail a generated view in which any
   expression binding names `{view.custom.<name>}` for a `<name>` that is not a key of the view's `custom`, naming the
   view and the property. It runs inside `screen.py` before any import, so a build with such a view refuses to import.
